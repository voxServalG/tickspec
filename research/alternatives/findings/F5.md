# F5: LLM/AI-Based Approaches to Strategy Description and Generation

**Research angle**: Do LLMs make hand-crafted DSLs like tickspec unnecessary?
**Date**: 2026-08-07
**Note**: External web search/fetch was unavailable during research. Findings are based on training data knowledge through early 2025. URLs and version numbers should be verified.

---

## 1. Landscape Overview

The LLM/AI trading strategy space breaks into four categories:

| Category | Examples | tickspec relevance |
|----------|----------|-------------------|
| LLM-as-code-generator | Prompt → Python/Pine Script | Direct competitor for strategy authoring |
| AI agent frameworks | FinGPT, FinRL, TradingGPT | Different layer — execution, not description |
| NL-to-DSL translators | Various research prototypes | Could complement or replace DSL |
| LLM-augmented IDEs | GitHub Copilot, Cursor for quant | Augments existing code, doesn't replace DSL |

## 2. Detailed Findings

### 2.1 FinGPT (AI4Finance Foundation)

**What it is**: Open-source LLM framework specifically for finance. Built on top of LLaMA/BLOOM/ChatGLM with financial domain fine-tuning. Covers sentiment analysis, summarization, and — critically — trading signal generation.

**How it handles strategy description**:
- Uses structured prompts with financial context (news, sentiment, price data)
- Strategies are described in natural language within a prompt template
- The LLM outputs trading signals (buy/sell/hold) rather than strategy code
- Architecture: data pipeline → LLM fine-tuning → signal generation

**Portable/auditable representation?**: No. The "strategy" is embedded in model weights and prompt templates. You can version-control the prompt, but the model's behavior changes with fine-tuning updates. Not auditable in any formal sense.

**Deterministic/reproducible?**: No. LLM inference is stochastic. Even with temperature=0, different hardware, quantization, or model versions produce different outputs. The same prompt on the same model can yield different signals across runs due to floating-point non-determinism.

**Could replace a DSL?**: No. FinGPT operates at a different layer — it's a signal generator, not a strategy specification tool. It produces *decisions*, not *descriptions*.

**Key quote from project**: "FinGPT democratizes financial LLMs" — the focus is on accessibility of AI for finance, not on formal strategy representation.

**GitHub**: `AI4Finance-Foundation/FinGPT` (5k+ stars as of early 2025)

---

### 2.2 FinRL / FinRL-Meta (AI4Finance Foundation)

**What it is**: Deep reinforcement learning framework for quantitative trading. FinRL-Meta extends it with a data-centric market simulator.

**How it handles strategy description**:
- Strategies are defined as RL environments (state space, action space, reward function)
- The "strategy" is the trained policy network — not human-readable
- Configuration is done through Python dictionaries/objects, not natural language
- Environment design is the closest thing to "strategy description"

**Portable/auditable representation?**: Partially. The environment definition (Python code) is portable. The trained model weights are portable but opaque — a neural network policy is not interpretable. You can audit the reward function but not the learned behavior.

**Deterministic/reproducible?**: With fixed seeds and identical hardware, yes for training. But the learned policy's behavior in novel market conditions is unpredictable. Training is highly sensitive to hyperparameters.

**Could replace a DSL?**: No. FinRL requires deep ML expertise to set up. The "strategy description" is an RL environment specification — far more complex than a DSL. It's a different paradigm entirely.

**Key papers**:
- Liu et al., "FinRL: A Deep Reinforcement Learning Library for Automated Stock Trading in Quantitative Finance" (2021)
- Liu et al., "FinRL-Meta: Market Environments and Benchmarks for Data-Driven Financial Reinforcement Learning" (2022)

### 2.3 BloombergGPT (Bloomberg, 2023)

**What it is**: A 50B-parameter LLM trained on Bloomberg's proprietary financial data corpus (363B tokens of financial data + 345B tokens of general data).

**How it handles strategy description**:
- Primarily a financial NLU model — sentiment, NER, QA, summarization
- Not designed for strategy generation per se, but can answer financial questions
- Could theoretically generate strategy code via prompting, but this isn't its focus
- Closed-source; only available through Bloomberg Terminal

**Portable/auditable?**: No. Proprietary, closed-source, behind Bloomberg Terminal paywall.

**Deterministic?**: No — standard LLM non-determinism applies.

**Could replace a DSL?**: No. It's a general financial LLM, not a strategy specification tool.

**Key paper**: Wu et al., "BloombergGPT: A Large Language Model for Finance" (2023), arXiv:2303.17564

### 2.4 TradingGPT / FinAgent-style Multi-Agent Systems

**What it is**: A category of research (2023-2024) that uses multiple LLM agents to simulate trading teams — e.g., an analyst agent, a risk agent, a portfolio manager agent.

**Notable examples**:
- **TradingGPT** (arXiv:2309.03736): Multi-agent LLM system with memory-augmented agents for trading decisions
- **FinAgent** (various papers): LLM agents that use tools (code execution, web search, data APIs) to make trading decisions
- **FinRL-LLM** integration: Combines RL agents with LLM reasoning

**How it handles strategy description**:
- Strategies emerge from agent interactions, not from explicit specification
- Each agent has a role description (prompt) and tools
- The "strategy" is the combination of agent prompts, tool access, and interaction protocol
- Some systems use a "portfolio manager" agent that synthesizes recommendations

**Portable/auditable?**: The agent prompts are portable. The agent interactions and decisions are logged (if implemented), providing some audit trail. But the emergent behavior is not formally specified — it's the result of LLM reasoning, which is opaque.

**Deterministic?**: No. Multi-agent LLM systems are inherently non-deterministic. Agent conversations vary across runs.

**Could replace a DSL?**: No. These systems are for *executing* trading decisions, not for *specifying* strategies. They operate at a higher level of abstraction.

### 2.5 Natural Language → Code Generation for Trading

**What it is**: The most direct competitor to a formal DSL. Users describe strategies in English, and an LLM generates executable code.

**Notable implementations**:

#### a) Pine Script / TradingView + ChatGPT
- Users describe strategies in natural language to ChatGPT
- ChatGPT generates Pine Script code for TradingView
- Extremely popular workflow (thousands of YouTube tutorials)
- **Problem**: Generated code is often buggy, uses deprecated APIs, doesn't handle edge cases
- **Auditability**: You get code, but it's not guaranteed to match the intent
- **Determinism**: Same prompt → different code on different runs

#### b) QuantConnect + LLM Integration
- QuantConnect's platform supports natural language strategy description
- LLM generates C#/Python code for the LEAN engine
- Better than raw ChatGPT because it has platform-specific context
- **Problem**: Code quality varies; requires human review

#### c) Capitalise.ai
- Commercial platform: "Describe your strategy in plain English → automated execution"
- Uses NLP (not necessarily LLM) to parse natural language into trading rules
- Supports conditions like "If AAPL drops 5% in 1 hour, buy $10,000"
- **Determinism**: More deterministic than LLM approaches — uses rule-based NLP
- **Auditability**: Translates NL to visual flowcharts for review
- **Limitation**: Limited to simple conditional strategies; can't express complex multi-factor models

#### d) Research: NL-to-SQL/Code for Financial Data
- Multiple papers on using LLMs to query financial databases via natural language
- "Text2SQL" for financial data (e.g., "Show me stocks with P/E < 15 and revenue growth > 20%")
- These generate *queries*, not *strategies*, but the boundary is blurry

### 2.6 AI-Augmented Development (Copilot/Cursor for Quant)

**What it is**: General-purpose AI coding assistants used by quants to write strategy code faster.

**How it handles strategy description**:
- Quant writes partial code or comments → AI completes the code
- Works with any language (Python, C++, Pine Script, etc.)
- The strategy is still expressed in code, not natural language
- AI assists with boilerplate, indicators, backtesting scaffolding

**Portable/auditable?**: Yes — you get standard code. The AI is just a faster way to write it.

**Deterministic?**: The output code is deterministic (it's normal code). The generation process isn't, but that doesn't matter — you review and commit the code.

**Could replace a DSL?**: Paradoxically, AI coding assistants *reinforce* the value of DSLs. A well-designed DSL with good type hints and documentation gets better AI completions. Copilot with tickspec could be more productive than Copilot with raw Python.

## 3. Analysis: The Key Question

### Does the rise of LLMs make hand-crafted DSLs unnecessary?

**Answer: No. They serve different purposes and are complementary.**

Here's the breakdown:

#### What LLMs are good at (that DSLs aren't):
1. **Rapid prototyping**: "Give me a mean reversion strategy on AAPL" → working code in seconds
2. **Exploration**: Trying out ideas without learning a new syntax
3. **Translation**: Converting a strategy described in a blog post into executable code
4. **Education**: Explaining what a strategy does in plain English

#### What DSLs are good at (that LLMs aren't):
1. **Auditability**: Every line of a DSL has a precise, verifiable meaning. LLM output requires human review.
2. **Determinism**: Same DSL file → same IR → same behavior. Always. LLMs are stochastic.
3. **Team collaboration**: A DSL file can be code-reviewed, version-controlled, and shared. An LLM prompt is ambiguous.
4. **Regulatory compliance**: Financial regulations require auditable, reproducible trading logic. LLM-generated code doesn't meet this bar without extensive manual review.
5. **Type safety**: A well-typed DSL catches errors at compile time. LLM output has no guarantees.
6. **Portability**: A DSL compiles to a stable IR. LLM output changes with model updates.

#### The real relationship:

```
Natural language (LLM input)
    ↓ [LLM generates]
DSL code (e.g., .tksp files)
    ↓ [DSL compiler]
Canonical IR (JSON)
    ↓ [Platform adapters]
Executable strategy
```

**LLMs are a better *input interface* for DSLs, not a replacement.**

The ideal workflow:
1. User describes strategy in English
2. LLM generates tickspec DSL code
3. DSL compiler validates and produces IR
4. IR is auditable, deterministic, and portable

This gives you the accessibility of natural language with the rigor of a formal specification.

## 6. Implications for tickspec

### Direct threats to tickspec from LLMs:
- **Low**: LLMs generate code in general-purpose languages (Python, Pine Script), not domain-specific representations
- **Low**: LLM output lacks the auditability guarantees that a formal DSL provides
- **Medium**: For *simple* strategies, LLM → Python might be "good enough" without a DSL

### Opportunities for tickspec with LLMs:
- **High**: LLM as a tickspec code generator (NL → .tksp → IR)
- **High**: LLM to explain/translate existing .tksp files to natural language
- **Medium**: LLM to suggest optimizations or flag issues in .tksp files
- **Medium**: tickspec as a "ground truth" format that LLM output is validated against

### Strategic recommendation:
**Position tickspec as the "compilation target" for AI-generated strategies, not as a competitor to AI.** The value proposition becomes:

> "Use any AI tool to draft your strategy. Then compile it to tickspec for auditability, determinism, and team review. The DSL is the bridge between AI creativity and production rigor."

## 8. Conclusion

LLMs and formal DSLs are **complementary, not competing** technologies:

- **LLMs democratize access**: Anyone can describe a trading idea in English and get code
- **DSLs guarantee rigor**: Formal specifications ensure auditability, determinism, and correctness
- **The pipeline matters**: NL → LLM → DSL → IR → Execution combines the best of both

The rise of LLMs actually *increases* the need for formal representations like tickspec, because:
1. LLM-generated code needs a validation target
2. Regulatory bodies will require auditable strategy representations
3. Teams need a shared, unambiguous strategy specification
4. Backtesting reproducibility demands deterministic inputs

**tickspec's moat is not "easier than Python" — it's "more auditable than LLM output."**
