# F4: Industry Standards for Trading Signal/Strategy Representation

> Research angle 4 — does any existing industry standard cover "declare signal logic → combine → produce operation"?

## Executive Summary

**No.** Every major financial industry standard operates at the **execution/order layer**, not the **signal/strategy layer**. The gap between "I have a trading idea expressed as composable signals" and "submit this order to the exchange" is entirely unstandardized. Standards cover *what to do* (order submission, trade reporting, risk limits) but never *how to decide* (signal logic, factor combination, strategy rules).

---

## 1. FIX Protocol (Financial Information eXchange)

### What it is
The dominant electronic trading protocol since 1992. Tag-value message format. Used by essentially all institutional trading desks, exchanges, and brokers worldwide. Maintained by FIX Trading Community (formerly FPL).

### Does it cover signals/strategies?
**No.** FIX is exclusively an **order-routing and execution protocol**. Its message types cover:

- **New Order Single (MsgType=D)** — submit an order
- **Execution Report (MsgType=8)** — order fills/status
- **Order Cancel/Replace** — modify orders
- **Market Data (MsgType=W/X)** — price/quote feeds
- **Security Definition** — instrument metadata
- **Allocation** — post-trade allocation

There is no message type for "signal," "factor," "strategy definition," or "indicator." FIX assumes a **prior decision has already been made** — it only transmits the result (an order).

### Relevant FIX concepts (closest approximation)
- **StrategyParameter** repeating group (in some messages) — allows attaching key-value parameters to execution strategies (e.g., VWAP/TWAP algorithm parameters), but this describes *how to execute*, not *how to decide*
- **TradingSessionID** — can route to specific algorithmic strategies, but these are broker-side black boxes
- **Indication of Interest (IOI)** — expresses trading interest but is not a signal specification

### Declarative?
No. Imperative message-passing protocol.

### Would it work for signal combination → operation?
**No.** FIX is the wrong abstraction layer entirely. It's the transport *after* the decision. A TickSpec-like system could *output* FIX orders, but FIX cannot express the logic that produces them.

### Used in practice for strategy description?
No. Strategy description is proprietary (Python, C++, in-house DSLs) at every trading firm.

## 2. FpML (Financial Products Markup Language)

### What it is
An XML-based standard for over-the-counter (OTC) derivatives messaging. Maintained by ISDA (International Swaps and Derivatives Association). Covers trade confirmations, position reporting, risk valuations for products like swaps, options, and structured products.

### Does it cover signals/strategies?
**No.** FpML describes **financial products and their lifecycle events**, not trading signals or strategies. Its scope includes:

- **Trade confirmation** — what was traded (product terms, counterparties, dates)
- **Position reporting** — current holdings
- **Risk/valuation** — mark-to-market, sensitivities
- **Novation/amendment** — trade lifecycle changes

FpML can describe complex structured products (e.g., a basket option with barriers), but this is **product definition**, not **strategy logic**. The distinction: FpML says "this is a 5Y EUR swap with these terms" — it does not say "buy when RSI < 30 and MACD crosses above signal line."

### Relevant FpML concepts (closest approximation)
- **Strategy** element in FpML exists but means "a combination of derivative legs into one trade" (e.g., a straddle = call + put), NOT a trading signal strategy
- **Basket** — describes a portfolio of underlyings, but as static composition, not dynamic rules

### Declarative?
Yes, XML is inherently declarative. But it declares *product structure*, not *decision logic*.

### Would it work for signal combination → operation?
**No.** Wrong domain entirely. FpML is about describing *what was traded* in OTC derivatives, not *when/why to trade*.

### Used in practice for strategy description?
No. OTC derivatives traders do not use FpML for strategy logic. FpML is used post-trade for confirmations and regulatory reporting.

## 3. OMG Financial Standards / FIBO

### What it is
The Object Management Group maintains several financial ontologies and standards:

- **FIBO (Financial Industry Business Ontology)** — an OWL/RDF ontology defining financial concepts (accounts, instruments, parties, contracts, loans, securities, indices)
- **FCT (Financial Common Types)** — shared data types
- Various UML-based models for financial processes

FIBO is now maintained under the EDM Council.

### Does it cover signals/strategies?
**No.** FIBO is a **knowledge ontology** — it defines what financial things *are* (a stock is a type of security, a bond has a coupon, an index is computed from a basket). It does not model:

- Trading signals or indicators
- Factor models or scoring logic
- Strategy combination rules
- Execution triggers

The closest concept might be an **InvestmentStrategy** class in some financial ontologies, but these describe strategy *categories* (long/short equity, global macro) as taxonomy labels, not executable logic.

### Relevant concepts (closest approximation)
- **Index** — FIBO defines how indices are composed (market-cap weighted, equal-weighted), which is a form of rule-based combination. But this is *passive composition*, not *active trading logic*
- **ContractualProduct** / **Strategy** — product-level, not signal-level
- **Event** — trade events, not signal triggers

### Declarative?
Yes (OWL/RDF is declarative knowledge representation). But it declares *domain knowledge*, not *trading logic*.

### Would it work for signal combination → operation?
**No.** FIBO could provide useful *vocabulary* (defining what "momentum," "mean reversion," or "signal" means in financial terms) but cannot express executable strategy logic.

### Used in practice for strategy description?
No. FIBO is used for data governance, regulatory reporting ontologies, and semantic interoperability — not for trading system logic.

## 4. ISO 20022

### What it is
A global standard for financial messaging, developed by SWIFT and now mandated by many central banks and payment systems. Uses XML Schema (XSD) for message definitions. Covers:

- **Payments** (pacs.* messages) — payment clearing and settlement
- **Securities** (sese.* messages) — securities settlement, transfer
- **Trade** (trad.* messages) — trade confirmation and matching
- **Reference data** — instrument and party identification

Adopted by: ECB (T2), Fed (Fedwire), Bank of England, EBA Clearing, and many others.

### Does it cover signals/strategies?
**No.** ISO 20022 is a **post-trade and payments messaging standard**. Its securities messages cover:

- **sese.023** — SecuritiesSettlementTransactionInstruction (settle this trade)
- **sese.025** — SecuritiesSettlementTransactionConfirmation
- **Seev.031** — Corporate action notification
- **auth.012** — Authorization of a securities transaction

There is no concept of "signal," "indicator," "factor," or "strategy" in ISO 20022. It assumes the trading decision has been made elsewhere.

### Relevant concepts (closest approximation)
- **InvestigationExecution** — for investigating settlement failures, not strategy execution
- **Order types** — references to order types in settlement messages, but these are FIX-like execution concepts
- No signal, factor, or strategy message types exist

### Declarative?
Yes (XML Schema-based). But it declares *message structure for settlement flows*, not *decision logic*.

### Would it work for signal combination → operation?
**No.** ISO 20022 operates at the settlement and payments layer — even further downstream than FIX from the signal/strategy layer.

### Used in practice for strategy description?
No. ISO 20022 is used by infrastructure providers (clearinghouses, central banks, CSDs) for post-trade processing. Trading desks never interact with it for strategy purposes.

## 5. MDDL (Market Data Definition Language)

### What it is
An XML-based standard for market data representation, originally developed by the Financial Information Services Division (FISD) of the Software & Information Industry Association (SIIA). Intended to standardize how market data is described and exchanged.

### Current status
**Largely defunct.** MDDL never achieved widespread adoption. It was overtaken by:
- **RDF/semantic web** approaches for data modeling
- **JSON/REST APIs** for market data delivery
- Proprietary feeds (Bloomberg B-PIPE, Refinitiv Elektron)

### Does it cover signals/strategies?
**No.** MDDL describes **market data structure** — what a quote is, what a trade is, what an index value is. It models:

- **Market data events** (quotes, trades, volumes)
- **Instrument reference data** (what an instrument is)
- **Derived data** (calculated fields like VWAP, but as data definitions, not computation logic)

MDDL could describe *what data looks like* but not *what to do with it*. The "derived data" concept is the closest — defining that VWAP = volume-weighted average price — but this is a single-passive-aggregation definition, not a composable signal logic system.

### Relevant concepts (closest approximation)
- **DerivedData** — defines calculated market data fields
- **Analytics** — some support for analytics definitions, but as data types, not executable rules
- No concept of signal combination, factor weighting, or strategy rules

### Declarative?
Yes (XML-based). But it declares *data schemas*, not *decision logic*.

### Would it work for signal combination → operation?
**No.** Even if MDDL were thriving, it would only help standardize *data inputs* to a strategy, not the strategy logic itself.

### Used in practice?
Barely. MDDL is essentially dead as a standard. No significant adoption in modern trading infrastructure.

## 6. W3C / Industry Consortium Work

### What exists
There is **no W3C standard** for trading signals or strategy description. The closest relevant efforts:

#### W3C RIF (Rule Interchange Format)
- A general-purpose rule interchange standard (2013, now W3C Recommendation)
- Could theoretically express "if RSI < 30 then buy" as a rule
- **Not adopted in finance** — too academic, too generic
- Not designed for real-time trading signal evaluation

#### W3C SSN/SOSA (Semantic Sensor Networks Ontology)
- Models sensors, observations, and procedures
- A trading signal could be modeled as a "sensor" observing market conditions
- **Not adopted in finance** — designed for IoT/sensor networks

#### CFI (Classification of Financial Instruments) — ISO 10962
- Classifies instrument types (equity, bond, option, etc.)
- **Not about signals or strategies** — just instrument taxonomy

#### XBRL (eXtensible Business Reporting Language)
- Financial reporting standard (used by SEC, etc.)
- Describes financial statements, not trading logic

#### No consortium has tackled this
The reason is straightforward: **trading strategy logic is the core intellectual property of trading firms**. No firm wants to standardize or share how they make trading decisions. Standards exist for the *plumbing* (order routing, settlement, market data feeds) because interoperability at that layer benefits everyone. But standardizing strategy logic would benefit no one — it would commoditize alpha generation.

## The Gap

The signal/strategy layer exists in a **standardization vacuum**:

```
[Market Data]  →  [Signal/Factor Logic]  →  [Strategy Combination]  →  [Order Generation]  →  [Execution/Settlement]
  MDDL              ???                       ???                        FIX                   ISO 20022
  Bloomberg                                                  Python/C++                     FpML
  Refinitiv                                                  Proprietary DSLs
```

Every layer except the middle two has standards. The middle — where TickSpec operates — is entirely proprietary:

- **Quantitative hedge funds** use proprietary Python/C++/R frameworks
- **Retail platforms** (TradingView, MT4/MT5) have their own scripting languages (Pine Script, MQL)
- **Academic/backtesting** frameworks (Zipline, Backtrader, QuantConnect) use Python APIs
- **No interoperable standard exists** for declaring signal logic, combining signals, or mapping signal combinations to operations

### Why no standard exists

1. **Competitive advantage**: Strategy logic is IP. Firms resist standardization.
2. **Heterogeneity**: Different strategies need fundamentally different primitives (statistical factors vs. rule-based vs. ML-based).
3. **Execution coupling**: Many strategies are tightly coupled to execution details (order types, venue routing, latency requirements).
4. **No regulatory driver**: Regulators standardize reporting and settlement, not strategy logic. MiFID II requires algo trading disclosure but not strategy description format.

### Implications for TickSpec

TickSpec is not competing with any existing standard. It fills a genuine gap. The relevant comparison points are:

- **Pine Script / MQL** — the closest existing "signal DSLs" but proprietary and vendor-locked
- **Zipline/Backtrader API** — programmatic but not declarative, not portable
- **TradeStation EasyLanguage** — legacy, proprietary, limited

TickSpec's declarative YAML approach for "declare signals → combine → produce operations" has no direct standard predecessor. This is both a validation (no competition) and a risk (no established ecosystem to tap into).

---

## Key Takeaway

**No industry standard covers the "signal combination → operation" model.** Standards cover execution (FIX), settlement (ISO 20022), product definition (FpML), data schemas (MDDL), and domain ontology (FIBO). The strategy/signal layer is the wild west — every firm builds its own. TickSpec would be filling a genuine gap in the standards landscape, not duplicating existing work.
